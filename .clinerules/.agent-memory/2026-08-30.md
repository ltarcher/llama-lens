## CLI 整体重设计（llamalens）

### 任务
- 用户（BOSS，已睡觉，禁止提问）："现在项目里面的 cli 根本不能用，你整体全部重新设计并修复"

### 根因
- 旧 `cli/` 是 Go「本机单主机采集器」（~4243 行 / 15 文件）：本地读 /proc + journalctl，`ValidateLocalOnly` 拒绝非本机 llama 端点
- 用户真实 llama-server 在远程 ai.lan（10.0.0.28），由后端经 SSH 采集；开发容器无 llama-server/GPU → 本地采集器永远空视图，指向远程又被拒 → 两条路都死，故"根本不能用"

### 方案
- CLI 重设计为 **LlamaLens 后端的终端客户端**（与 Web 面板同源：轮询 REST 渲染 ANSI TUI，不直接连 llama-server）；删除本地采集器（备份 /tmp/llamalens-cli-old/）
- 新代码 7 文件 1724 行，仅依赖 x/term + x/sys：`cli/main.go`（flag+模式分发）、`cli/internal/client/{model.go,client.go}`、`cli/internal/tui/{format.go,render.go,tui.go}`
- 模式：门户 TUI（j/k/Enter/q）、`--host <id>` 详情 TUI（b/Esc/q/r）、`hosts [--json]`、`--once [--host]`、`--json` NDJSON、`--backend`/env `LLAMALENS_BACKEND`、`--interval`、`--no-color`、`--no-alt`、`--version`

### Bug
1. **Esc 返回键 advertised 未实现**：主机详情页脚写 "b/Esc 返回门户"，代码只处理 b。修复：viewHost 增加 keyEsc(27)。
2. **独立 Esc 与 ESC 序列（方向键）区分**：首版用 `os.Stdin.SetReadDeadline(50ms)` 探测，本环境返回 `file type does not support deadline`（PTY 不可 poll），探测读永久阻塞（最小 Go 实验证实）。修复：`unix.FcntlInt(F_GETFL/F_SETFL)` 临时把 stdin 置 O_NONBLOCK 探测下一字节——有字节=序列（整体吞掉），EAGAIN=独立 Esc；探测后恢复原 flags。
3. 注意：Go 1.25 工具链已移除 `syscall.FcntlInt`，必须用 `golang.org/x/sys/unix.FcntlInt`（x/sys 本就是 x/term 的间接依赖，无新增外部依赖）。

### 验证
- go build / go vet / gofmt 全干净
- 非 TTY：--version、hosts（表格对齐）、hosts --json、--once（门户）、--once --host ai（overview JSON）、--json --host ai（NDJSON）、后端宕机（rc=1 + 明确错误信息）
- TTY（python pty 直连，绕过 harness PTY 层）：门户 1s 实时刷新、j/k 导航、Enter 进入详情（llama-server/GPU/系统/告警/事件完整渲染）、Esc 返回门户、方向键序列被吞无副作用、b 返回、q 退出（rc=0、终端状态恢复）、后端宕机错误帧
- 重要发现：Codex harness 的 PTY 层会吞掉 \r/\n 输入（j 有效但 Enter 无效）→ TUI 按键验证必须用 python pty.fork 直写字节

### 重要经验
- **CLI 应是后端的客户端，不是并行采集器**：单一数据源、与 Web 面板一致，避免采集逻辑双份维护
- 本容器 Go 构建配方（/root 只读）：`cd cli && GOPATH=/tmp/gopath GOMODCACHE=/tmp/gomodcache GOCACHE=/tmp/gocache /usr/local/go/bin/go build -o llamalens .`（go 在 /usr/local/go/bin/go，1.23 自动拉 1.25 工具链）
- TUI 固定列宽必须截断（pad() 超宽不截断会列错位）；Enter 键须兼容 \r(13)/\n(10)
- 本环境 PTY 上 `SetReadDeadline` 不可靠（file type does not support deadline），按键探测用 O_NONBLOCK

## CLI 整体删除（用户决定，当日晚些时候）

### 背景
- 用户实际使用反馈：TUI 显示"一屏幕全是字、排版全是乱的"，认为自测不充分，决定**不做 CLI**，要求全部删除

### 删除范围（已全部执行）
- `cli/` 目录整体删除（新客户端代码 7 文件 + 二进制 llamalens）
- README.md：移除"终端 CLI"功能列表项 + 「终端 CLI（llamalens）」小节
- docs/02-架构设计文档.md：移除 §8 终端 CLI，9-13 节重编号回 8-12（已验证无跨节引用受影响：docs/01:159 的 §8 指向自身阈值章节）
- /tmp/llamalens-cli-old/（旧本机采集器备份）与 /tmp 测试脚本全部删除
- 注意：旧 CLI 从未提交过 git（git log --all -- cli/ 为空），删除后无 git 历史可恢复

### 未解决（若未来重做 CLI 需先查清）
- 用户终端排版混乱的根因未确认。python pty（80 列）测试中布局正常，疑似方向：
  1. CJK 双宽字符未计入列宽计算（pad/trunc 按 rune 数算，中文在终端占 2 列 → 列错位）
  2. 用户终端对备用屏（\x1b[?1049h）/ \x1b[H 覆盖重绘的处理差异 → 帧追加导致"一屏幕全是字"
  3. 窄终端下的自适应边界
- 经验：TUI 类交付必须考虑 CJK 显示宽度（wcwidth 语义），且要在用户真实终端环境验证，不能只信 pty 测试

### 决定
- CLI 不再是项目组成部分；后续开发不涉及 cli/
