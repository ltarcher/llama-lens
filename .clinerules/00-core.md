# Cline 核心工程规则

> 本文件是所有任务的最高优先级工程规则。\
> 目标不是让 Cline "更快写代码"，而是让 Cline
> 在修改代码之前先理解系统，并对最终结果负责。

## 1. 核心原则

### 1.1 证据优先

所有技术判断优先依据：

1.  当前项目代码
2.  当前项目配置
3.  当前测试
4.  Git 历史
5.  用户明确提供的信息
6.  明确指定的参考项目

禁止仅凭经验猜测。

如果存在多个可能原因，必须先调查并缩小范围，再决定修改方案。

### 1.2 根因优先

不要只修复用户举出的症状。

用户给出的例子只是一个表现，必须主动检查：

-   相同调用链
-   相同数据结构
-   相同组件
-   相同规则
-   相同 API
-   相同设计模式
-   同类边界条件

目标是解决产生问题的机制，而不是只让一个例子看起来正常。

### 1.3 理解之后再修改

任何代码修改之前必须：

1.  找到真实执行入口
2.  找到调用链
3.  找到实际 import / dependency
4.  确认真正生效的实现
5.  搜索同名类、函数、组件
6.  确认修改影响范围
7.  再决定修改文件

不能因为文件名看起来相关就直接修改。

### 1.4 最小必要修改

优先修改现有实现。

除非当前架构确实无法满足需求，否则：

-   不随意重构
-   不随意增加依赖
-   不随意改变 API
-   不随意改变数据结构
-   不随意改变已有行为
-   不顺手处理与当前任务无关的问题

### 1.5 保护用户已有修改

执行任何修改前先检查 Git 状态。

如果发现已有用户修改：

-   不覆盖
-   不回滚
-   不重置
-   不使用破坏性命令清理

只能在明确知道修改属于当前任务时处理。

### 1.6 PLAN 与 ACT 严格分离

PLAN：

-   调查
-   阅读
-   搜索
-   分析
-   设计
-   制定测试方案

PLAN 禁止修改任何文件。

ACT：

-   根据已经批准的方案实施
-   测试
-   Review
-   修复

不得在 PLAN 中"先试着改一下"。

### 1.7 测试通过不等于任务完成

必须验证：

> Requirement → Acceptance Criteria → Evidence

不能只执行一个 test 命令就宣布完成。

### 1.8 不把环境问题当默认答案

除非有证据，否则不要把问题归因于：

-   缓存
-   没重启
-   没 reload
-   HMR
-   用户操作

首先检查：

-   实际修改文件
-   实际执行代码
-   import 链
-   调用链
-   Console / 日志
-   构建错误
-   Git diff

如果确实需要重启或 reload 才能生效，明确说明原因。

## 2. 修改前强制检查

修改任何类、函数、组件或规则之前：

1.  搜索目标名称
2.  确认是否存在多个定义
3.  找到实际调用方
4.  追踪 import 链
5.  确认运行时使用的实现
6.  阅读上下文
7.  搜索同类实现
8.  明确影响范围
9.  再修改

## 3. 错误排查优先级

出现异常时，优先：

1.  查看完整错误信息
2.  查看 Console
3.  查看 Network
4.  查看后端日志
5.  查看 Stack Trace
6.  查看实际 API 请求和响应
7.  查看 Git diff
8.  追踪调用链
9.  建立多个假设
10. 用证据逐个排除

禁止：

> 猜一个原因 → 直接改代码 → 发现不对 → 再猜另一个。

## 4. 完成定义

只有满足以下条件才允许宣布完成：

-   [ ] 需求已经理解
-   [ ] 根因已经确认，或实现任务已经明确
-   [ ] 实际执行代码已经确认
-   [ ] 修改完成
-   [ ] Acceptance Criteria 已验证
-   [ ] 相关测试完成
-   [ ] 没有明显回归
-   [ ] Git diff 已检查
-   [ ] 没有无关修改
-   [ ] 必要的安全检查完成
-   [ ] 必要文档已经同步
-   [ ] 已知未完成事项已经明确说明

## 5. 最终报告

完成任务后统一输出：

### 任务

一句话说明。

### 根因

如果是问题修复，说明真正原因。

### 方案

说明采用的方案。

### 修改

逐文件说明主要修改。

### 测试

列出实际执行的测试及结果。

### Review

说明 Git diff、回归和风险检查结果。

### 风险

没有则写"无明显风险"。

### 未完成

没有则写"无"。

### 用户操作

如果不需要用户操作，明确写"不需要"。
