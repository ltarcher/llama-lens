## Top CPU"数据是假的"问题（根因修复）

### 现象
主机详情页 Top CPU 列表与 Top MEM 完全相同（同进程同顺序），且所有 CPU% 为 0.0，而进程卡显示 llama-server 100%+。

### 根因
`BATCH_CMD` 用 `ps -eo pid,comm,pcpu,pmem,rss,utime,stime`，但 procps 的列语义与预期不符：
- `stime` 列是 **start time（启动时间）**，不是 system CPU 时间（输出 `Aug28`/`08:53`）
- `utime` 列在 procps-ng（本机 3.3.17 / ai.lan 4.0.4）中不可用，输出 `-`
- `_i()` 解析失败 → utime+stime 恒为 0 → DiffEngine 差分 CPU% 恒 0 → 排序退化为 RSS 序（= Top MEM 副本）
- 上次对话加的 `_ticks` 累计 CPU 兜底排序也因此全是 0 而失效（治标未治本）

### 修复
- `ps -eo pid,comm,pcpu,pmem,rss,time`（time 列 = user+system 累计 CPU 时间，格式 `[[dd-]hh:]mm:ss`）
- 新增 `_ps_time_to_ticks()` 解析为时钟滴答（×CLK_TCK=100）；`parse_ps` 输出 `cpu_ticks` 字段
- 精度限制：ps time 列 1s 粒度（/proc/stat 是 10ms），低 CPU 进程（<25% 单核）在 2s 窗口内可能显示 0 或抖动；Top 列表主要看高 CPU 进程，可接受

### 验证
- 单测 21/21 通过（格式解析：hh:mm:ss / mm:ss / dd-hh:mm:ss / 非法值；ai.lan 真实样本行；差分 100%/50% 计算）
- 端到端（SSH 到 ai.lan 真实数据）：201 进程解析正常；Top CPU 与 Top MEM 顺序不同（按累计 CPU 时间兜底生效）；临时 CPU 满载进程实测 99.5% 且排 Top CPU 第 1（测试进程已清理）
- 注意：验证期间 ai.lan 的 llama-server 被用户重启过（PID 730121→774000），生成是突发式的（burst 间 CPU 为 0）

### 未完成 / 用户操作
- **运行中的后端（:8000）仍是旧代码，需用户重启才能生效**：Codex 沙箱无法 kill 沙箱外进程（kill 报 no such process，但 /proc 可读；自己子进程 kill 正常）。用户操作：`pkill -f "uvicorn backend.main:app"` 后 `./run.sh`（或原启动方式）
- 重启后验证：Top CPU 列表出现非 0 CPU% 且与 Top MEM 不同

## Top CPU 第二轮：ps time 1s 精度导致 CPU% 量化（根因修复）

### 现象
用户反馈 Top CPU/Top MEM "数据还是不对、没有来回跳动、一直静态显示"。截图里所有 CPU% 均为 0.0。

### 调查与根因
- 后端 09:16 已重启（跑的是上午的 ps time 修复版），Top CPU 排序已正确（按累计 CPU 时间兜底，与 Top MEM 不同序）
- 用户截图是 llama-server 空闲时段（RSS 6.5GB，后涨到 11.4GB）——空闲时全 0.0 本身正确，但：
- **真正缺陷：`ps time` 列只有 1s 粒度**。2s 采样窗口下 Δticks 只能是 0/100/200/300 → CPU% 被量化成 0/50/100/150 台阶值。实测 API 连续 3 次采样：141.5% → 47.3% → 0.0%（6 秒内跳变），低负载进程（<25% 单核）几乎恒 0 → 表格看起来"静态/是假的"
- 前端无问题：WS 1s 推送正常，topCpu/topMem 为响应式 computed，dist 与 src 同步（08:43 构建后 src 未再改）

### 修复
- BATCH_CMD：`ps -eo pid,comm,pcpu,pmem,rss`（去掉 time 列）+ 新增 `==PSTICKS==` 段：单条 awk 读全部 `/proc/[0-9]*/stat` 的 utime/stime（字段 14/15，10ms 粒度），输出 `pid utime stime`
  - awk 要点：`FNR==1` 每文件首行；`index($0, ") ")` 定位 comm 结束（comm 含空格/括号也安全）；`split(FILENAME, p, "/")` 取 p[n-1] 为 PID；`m >= 13` 校验字段数
- `parse_ps` 改 5 列解析；新增 `parse_ps_ticks()` → {pid: utime+stime}；snapshot 按 PID 关联（缺失记 0，负增量由 DiffEngine 钳制 0）
- 删除 `_ps_time_to_ticks()`（死代码）及 CLK_TCK import
- 实测开销：awk 段 200 进程，SSH 往返无感知增加（0.12~0.48s）

### 验证
- 单测：parse_ps（5 列/comm 含空格/坏行）、parse_ps_ticks（真实样本/坏行）、DiffEngine（141.5%/10%/负增量钳制 0）、split_sections 识别 PSTICKS —— 全过
- 端到端（SSH ai.lan 真实数据）：PSTICKS 200 行正常；受控负载 A=100% 忙循环实测 99.9%、B=真 50% 占空比（烧 1s+睡 1s）实测 56.7%；htop 1.0%、nvidia-smi 0.3% 等细粒度值（旧方案只能出 0/50/100/150）；测试进程已清理
- 注意：`while :; do sleep 1; done` 不是 50% 负载（bash 在等 sleep 子进程，自身 CPU≈0），做占空比测试要用"烧 CPU 1s + sleep 1s"

## "SSH 断开"（双主机）+ tvai 日志挂起（根因修复）

### 现象
- 两主机 UI 均显示"SSH 断开"，CPU —/MEM —，后端日志**零痕迹**（无连接失败、无异常）
- tvai 额外有周期性重连（约 17.5s/轮）
- 用户报"llama 离线 配置正确的 连不上"——tvai 的 llama 离线实为机器 09:37 重启、llama-server 10:00:01 才启动（PID 5148），后端 10:02 起自恢复 llama_online=true，**非 Bug**

### 根因
1. **主因（双主机）**：上一轮 Top CPU 精度修复往 `BATCH_CMD` 新增的 `==PSTICKS==` awk 行**未转义 `{`/`}`**。`_build_batch_cmd()` 用 `BATCH_CMD.format(...)` → 首个 `_cycle` 即 `ValueError: unexpected '{' in field name` → SshPoller 的 asyncio 任务死亡。HostMonitor._tasks 持有 task 引用但异常从未被 retrieve → **零日志静默死亡** → `metrics["reachable"]` 恒 False → `ssh_ok=false`。同文件 DISKIO 行已有 `{{print}}` 转义先例，PSTICKS 行漏了
2. **健壮性缺陷**：SshPoller.start() / LogPoller.start() 循环体均无 try/except，任何单周期异常都会永久杀死 poller 且无日志
3. **tvai 专属**：hosts.yaml 中 tvai `log.source: file` 但 `log.path` 被注释（空）→ LogPoller boot-block 命令变成 `tail -n 50000  2>/dev/null | grep ...` → tail 无文件参数读 SSH channel stdin（paramiko 永不关闭）→ 15s 挂起 → `socket.timeout`（**空消息**）→ 日志"SSH 命令执行失败: "（空）→ `_drop()` 杀掉共享连接 → 下轮 `open_stream` AttributeError 'NoneType'。实测复现：`timeout: ''` 6s

### 修复
- `backend/pollers/ssh_host.py`：PSTICKS awk 行花括号转义（`{{`/`}}`）；`SshPoller.start()` 循环体 try/except → `log.exception` + `reachable=False` + 继续下一周期
- `backend/pollers/log_poller.py`：`start()` 顶部守卫——`source==file 且无 path` → `log.error` 明确报错 + `available=False` + return（快速失败，不挂起）；循环体 try/except
- `backend/pollers/ssh_conn.py`：两条 warning 日志加 `type(e).__name__`（空消息异常如 socket.timeout 原来日志里只剩冒号，排查代价大）

### 验证
- py_compile 3 文件通过；`BATCH_CMD.format()` 正常，输出 awk 行花括号配对；本地 awk 执行 rc=0
- 单测：parse_ps_ticks / split_sections（PSTICKS 段）/ parse_ps（5 列、comm 含空格）全过
- 端到端（真实 SSH 双主机）：ai reachable=true（cpu 1.57%、mem 7497MB、2 GPU、proc_found、top 列表真实）；tvai reachable=true（cpu 0.63%、mem 4506MB、1 GPU、proc_found）；LogPoller tvai 守卫 0.0s 返回 available=False
- 存活测试：人为制造周期异常 → 连续 4 轮"采集周期异常"ERROR（带 traceback）后 stop() 干净退出，任务未死

### 未完成 / 用户操作
- **运行中后端（PID 197222，09:45 启动）仍是旧代码**，/api/health 实测两主机 ssh_ok=false。用户操作：`pkill -f "uvicorn backend.main:app"` 后 `./run.sh`；重启后两主机应 ssh_ok=true
- **tvai 日志采集需用户决策**：llama-server stdout 在终端（/dev/pts/0），无日志文件。方案 A：重定向输出到文件 + hosts.yaml 配 `log.path`；方案 B：systemd 托管 + `source: journal`。未动用户的 gitignored config/hosts.yaml

### 重要经验
- 往 `str.format()` 模板（如 BATCH_CMD）里加 shell/awk 行时，字面 `{`/`}` 必须双写转义；同模板内找已有转义行做参照（DISKIO 行）
- asyncio 任务内异常若从未被 retrieve（无 await task / 无 done callback），任务静默死亡且零日志——长驻 poller 循环必须逐周期 try/except
- 异常消息可能为空（socket.timeout），日志必须带 `type(e).__name__`
- `tail` 不带文件参数会读 stdin；在 SSH channel 上 stdin 永不关闭 → 挂起到超时

### 为什么用后端守护（重要环境发现，勿重复调查）
- bwrap 沙箱 `--die-with-parent --new-session`：exec 会话结束后台进程即死；新 PID 命名空间（NSpid 2 层），/proc 显示宿主 pid 而 getpid() 返回命名空间 pid → 沙箱内测试必须用 Popen.pid，不能用 /proc 扫描的宿主 pid 做 os.kill
- /sys/fs/cgroup 只读 → system/user systemd 均无法 StartTransientUnit（ENXIO，连 /bin/true unit 都不行）；版本串 "247.3-7+deb11u2" 有误导性——实际 D-Bus 接口是 systemd 256+ 风格（StartTransientUnit 签名 ssa(sv)a(sa(sv))、无 GetState）；systemctl --user 失败但 busctl 可用
- 根文件系统只读（writable roots 之外）→ 无 cron、无 unit 文件、不能写 /etc /var /root
- pgrep/pkill 损坏（打印 "pgrep: uptime"、恒 exit 1）→ 用 /proc/*/cmdline 扫描或 Popen.pid
- 可挂靠的长寿进程：LlamaLens 后端 uvicorn 跑在 system.slice/system-code-server.slice/code-server@root.service 下，会话死亡后仍存活 → 由后端守护代理
